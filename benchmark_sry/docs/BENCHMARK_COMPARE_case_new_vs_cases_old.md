## 2. 差异原因（第一层）：两套 case **不是同一套题**

### 2.1 题量与题型分布不同

- `**cases`（cases_old）**：100 条；含 **5** 条 `anti_interference`、**20** 条 `decision_repeat_push` 等（与其它大类配比见仓库）。
- `**cases_new`（case_new）**：**81** 条；同类配比 **被裁剪**（例如抗干扰仅 **2** 条、P5 仅 **4** 条等）。

因此：**总分、通过率、各「率」类指标的分母与分子都不同**，不能把「42% vs 78%」直接等同于「系统变差一倍」。

### 2.2 同名 `case_id` 的题干也已改写

历史上对 `cases` 与 `cases_new` 做过对比：**出现在 `cases_new` 中的 `case_id`，与 `cases` 中同名条目的 JSON 内容并非逐字相同**（文案、期望子串、`project`、`events` 等均可不同）。

因此：**case_new 等价于「另一份题库」在同一条 Runner 上跑出来的成绩**，不是「只换了文件夹路径」。

---

## 3. 差异原因（第二层）：指标「断崖」背后的 **case_new 局部结构**

以下基于 `**benchmark_sry_report_2026-05-04_17-42-06_case_new.json`** 的统计（与 md 一致）。

### 3.1 `repeat_push_hit_rate = 0` 不等于「系统完全不会 recall」

- `cases_new` 里 **仅 4 条** `decision_repeat_push`（例如 `P5-PUSH-001`～`003` 与 `P5-PUSH-NEG-001`）。
- 这 **4 条在本次报告中第一条检查均未通过**（正例未命中期望、负例仍被召回等），故 Runner 汇总 `**0 / 4 = 0%`**。
- `cases_old` 侧有 **20 条** P5，其中多数正例通过，故 `**repeat_push_hit_rate = 0.75`**。

**系统不足仍可能存在**（例如负例抑制弱、正例子串与抽取不一致），但 **0% 在很大程度上是「小题集 + 全挂」的统计结果**，与「全量 20 条」不可直接比。

### 3.2 `contradiction_overwrite_success_rate = 0` 与 P4、P3 大量 partial

- case_new 中 **矛盾更新** 几乎全部为 **partial**，且 `**矛盾覆盖成功率` 为 0**——与「新结论可检索，但 **版本链（`superseded_by`）未建立** 或 **Top1 仍泄漏旧话术**」的检查失败一致。
- **上下文失效（P3）在 case_new 统计里可表现为「20 条全系 partial」**（新结论能搜到，但旧值 Top1 与覆盖链仍不过）。

这与系统在 `**store_decision` 相似决策判定 / 顶替链** 上的行为高度一致：**题库话术一变，「能否判定为同一决策槽的更新」随之变化**；`cases_new` 若更偏「大改写、跨栈替换」，则更容易全线拿不到链。

### 3.3 `stale_leakage_rate`：case_new 更低（0.05 vs 0.40）

该指标含义是：在 **矛盾更新类** case 中，「旧值在 Top1 泄漏」的比例。

- case_new 更低，**不一定**代表「系统更会防泄漏」；
- 常见情形是：**矛盾类 case 的写法或分支不同**，或 **Top1 根本不是旧决策文本**（例如检索返回其它碎片），导致「禁止子串」检测 **较少触发**。

解读时需结合 **分用例表**，不能单看一个比率。

### 3.4 抗干扰：2 条 vs 5 条，Recall 小数不可混谈

- case_new：**2** 条抗干扰 → Recall@1 = 0.5 表示 **约 1/2** 在 Rank1 命中。
- cases_old：**5** 条 → Recall@1 = 0.8 表示 **4/5** 命中。

样本极少时，**0.5 vs 0.8 更多是抽样波动 + 题干差异**，不宜过度解读为「系统抗干扰能力翻倍」。

## 4. 对应到「系统」的主要不足（能力缺口）

在承认 **题库与分母不同** 的前提下，两份报告共同指向、且在 **case_new 上被放大** 的问题包括：

### 4.1 决策更新与版本链（P3 / P4）

- **不足**：依赖 **字符串相似度** 等启发式判断「是否覆盖旧决策」；当新旧表述 **主题相同但措辞/栈名变化大** 时，`**superseded_by` 链常建不起来**，旧记录仍为 active，检索 **Top1 仍像旧结论**。
- **表现**：矛盾覆盖成功率在 case_new 上 **接近全线崩溃**；cases_old 上仍有一部分「局部修订」类 case 能过链。

### 4.2 检索排序与聚合结论位置（P1 抗干扰、P2 聚合）

- **不足**：语义检索 + 与 SQLite 结果合并排序时，**新写入 / 相似片段** 容易压在「锚点 / 拍板句」之上；抗干扰里 **回拨时间** 会加剧这一效应。
- **表现**：抗干扰 Rank、聚合「结论在 Top3」类检查，在 **不同题干** 下波动大。

### 4.3 主动 recall 的精确度（P5）

- **不足**：`recall_relevant_decisions` 对 **闲聊与方案讨论** 区分不足；负例里一旦仍含技术词，容易 **误召回**。
- **表现**：case_new 里 P5 **条数少且全挂** → 汇总命中率 **0%**；cases_old 条数多 → 可见 **约 75%** 的第一检查通过（仍有不少负例/边界失败空间）。

### 4.4 自动记账触发（P1 capture）

- **不足**：`chat_auto_record` 对「决策口吻」覆盖不全；题干稍换说法即 `**dry_run=skipped`**。
- **表现**：若 `cases_new` 捕获题改写偏多，会出现 **capture 失败集中**（需在具体 JSON 里按 `case_id` 看）。

---

## 5. 使用建议（如何避免误读）

1. **固定对比口径**：同一轮代码变更，应 **同时跑 `cases` 与 `cases_new`**，或只选其一作为「主基准」，避免混用历史报告数字。
2. **优先看分题型表**：阅读两份 `.md` 里 **「分用例结果」**，按 `case_type` 归类数失败项，而不是只看总分。
3. **cases_new 若作为下一代题库**：建议单独维护「与实现同步的 changelog」，并在 Runner 或文档中标明 **题量、题型配比变更**，否则汇总率会不可比。
