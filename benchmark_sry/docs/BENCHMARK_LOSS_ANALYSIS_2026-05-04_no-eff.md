## 2. 按题型归纳：丢分从哪来

### 2.1 P1 抗干扰（`anti_interference`）— 全部 partial，核心丢在「命中排位」

- **现象**：5 条（`P1-ANTI-001`～`005`）均为 **partial**。报告里 `extra.rank` 均为 **4**（即锚点决策在 `query_decisions` 返回列表中排到第 4 位），而用例要求 **`max_rank: 1`**（Recall@1），因此 **「抗干扰_命中」** 全部失败。
- **仍通过的子项**：**「抗干扰_噪声规模」**、**「抗干扰_旧值不泄漏」** 均为 True——说明噪声条数与 Top3 禁止子串未误伤，问题不在噪声脚本，而在 **「锚点 vs 干扰决策」谁排在更前**。
- **原因推断**：
  1. Runner 将 **锚点** 写入后 **回拨 `created_at`** 模拟「一周前」，随后写入的 **distractor_events（干扰决策）** 时间更新，在「按时间或默认排序」的检索逻辑下更容易占满前排。
  2. **查询语义** 与多条干扰决策更相近时，向量检索 / 混合排序会把干扰项顶到 Top3，锚点落到第 4。
- **改进方向（实现或题库二选一或并行）**：
  - 实现侧：抗干扰检索对「同 project + 锚点/决策关键词」加权，或对 **显式拍板句** 提高权重；或放宽 benchmark 的 `max_rank` 仅作阶段性指标（需与赛题定义一致再改）。
  - 题库侧：减少与 query 语义高度重叠的 distractor，或让 `expected_active_value` 与锚点 `decision` 字段抽取结果严格一致。

---

### 2.2 P2 决策聚合（`decision_aggregation`）— 7 条 partial，丢在「结论排位 >3」

- **现象**：`P2-AGG-001`、`002`、`003`、`012`、`017`、`019`、`020` 为 partial；报告里 **`rank=4`**，而 Runner 要求结论子串出现在 **Top3** 内（`rank <= 3`）。
- **原因推断**：同一 `project` 下按设计会写入 **4 条**（群聊 / 文档 / 评审 + `/decide` 拍板）。若每条都独立成一条决策记录，检索时前 3 条常被 **碎片句** 占满，**拍板句** 落在第 4 条，导致 **「聚合_结论命中」** 失败；**「聚合_证据命中」** 多数仍通过（`evidence_hits` 常 ≥ `source_count_min`），故为 partial 而非全挂。
- **改进方向**：
  - 实现侧：`query_decisions` 对含「最终口径 / 拍板」类 `decision` 提权，或合并同 topic 碎片为单一 active 记录（产品策略变化大，需单独设计）。
  - 题库侧：临时可把 `expected_active_value` 改为更易唯一命中的短子串，并把 query 与拍板句对齐；根本仍依赖排序。

---

### 2.3 P3 上下文失效（`context_invalidated`）— 13 条 partial，成对失败模式固定

- **现象**：未通过的 13 条均为 **同一模式**：
  - **「上下文失效_新结论可检索」**：True（新结论在 Top3 内能搜到）
  - **「上下文失效_旧值不在Top1」**：False（Top1 决策正文仍含禁止的旧话术子串）
  - **「上下文失效_存在覆盖关系」**：False（库内任意 `superseded_by` 未形成 Runner 期望的覆盖链）
- **原因推断**：Runner 依次写入 **initial → invalidating → updated** 三条。若 **`store_decision` 的相似决策合并 / supersede（顶替）** 未把「旧决策行」与「新决策行」链起来，则旧行仍为 **active**，检索排序时旧结论仍可能占 **Top1**；同时 DB 中看不到可用的 **supersede** 关系，第三项检查失败。
- **与通过用例对比**：全量 20 条里 **7 条 passed**（如 `P3-CTX-006`、`008`、`009`、`010`、`013`、`019`、`020`），说明 **部分话术组合** 能触发覆盖逻辑，**另一部分**（如典型 DB/消息队列/CI 等「大话题切换」）未触发。
- **改进方向**：在 `memory.store_decision`（或等价层）明确 **同 project + 同主题槽位（slot）** 的更新策略；或对「决定：…」类句式提高互覆盖的相似度召回，保证写入第三条后旧行 `superseded_by` 指向新行。

---

### 2.4 P4 矛盾更新（`contradiction_update`）— 11 条 partial，与 P3 同源问题

- **现象**：未通过的 11 条同样是：
  - **「矛盾更新_新值命中」**：True
  - **「矛盾更新_旧值不在Top1」**：False
  - **「矛盾更新_版本链成立」**：False（`decisions` 表中旧行 `superseded_by` 未指向新行 id）
- **通过的 9 条**：`P4-CONFLICT-001`、`002`、`004`、`008`、`011`、`012`、`016`、`017`、`018`（多为 **同一句式上的局部修订** 或 **数字/枚举级** 变更，例如周报 A/B、周一周二、验证码时长、备份天数档位、通知通道组合等）。
- **失败的典型**：发版窗口、主库选型、Kafka/RocketMQ、网关选型、采样率、发布策略、内部协议、权限模型、归档频率、Feature Flag 等 **「整句决策主体变化大」** 的 pair。
- **原因推断**：与 P3 一致——**仅当系统把两条决策识别为「同一记忆位的更新」** 时，才会写 `superseded_by` 并把旧结论从 Top1 挤下去；**大改写** 对被识别为「全新决策」时，旧记录仍 active，检索 Top1 仍是旧句，版本链检查失败。
- **改进方向**：产品/实现上为「矛盾更新」增加 **显式 topic id** 或 **决策键（decision key）**；或在评测侧暂时缩小 P4 话术到「必能触发 supersede」的句式（会降低 benchmark 难度，需你权衡）。

---

### 2.5 P5 决策重复（`decision_repeat_push`）— 负例全挂，正例全过

- **现象**：`P5-PUSH-001`～`015` 均 **passed**；`P5-PUSH-NEG-001`～`005` 均 **failed**。
- **失败检查**：**「重复决策_不应推送」** — `expected_reminder: false` 时期望 **召回为空或不命中**，实际 **`recalled=1`**（`recall_relevant_decisions` 仍返回至少一条决策）。
- **原因推断**：负例的 `trigger_message` 仍含与历史决策 **强相关的技术词**（如 Redis、MySQL、PKCE、10%、365 等），当前 **recall（召回）** 路径按关键词 / 向量仍会关联到已入库决策，**缺少「闲聊 vs 业务重提」的二次判别**。
- **改进方向**：
  - 实现侧：在 `recall_relevant_decisions` 增加 **意图/是否讨论方案** 的轻量过滤，或提高负例场景的相似度阈值。
  - 题库侧：负例触发句改为 **与决策文本几乎无 token 重叠** 的纯生活闲聊（避免「Redis 咖啡店」仍含 Redis）。

---

### 2.6 P1 决策捕获（`decision_capture`）— 仅 1 条整题失败

- **用例**：`P1-CAP-007`
- **现象**：**「candidate_触发」** 失败，`dry_run=skipped`（即 `auto_record_message` 未进入可记录的 dry_run 候选态）。
- **原因推断**：该条正文为「最终口径：告警分派使用值班机器人…」——**措辞未命中** `chat_auto_record` 当前对「可记录决策」的触发规则（与「决定/结论/拍板」等强触发词相比偏弱）。
- **改进方向**：扩展 `chat_auto_record` 对「最终口径」「分派」等模式的识别；或微调该条 case 文案以贴合现有规则（评测与产品对齐问题）。
